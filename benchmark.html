Compiler Benchmark — OpenSNES vs PVSnesLib

OpenSNES figures: make bench (devtools/cyclecount/bench.py, which CI compares against devtools/cyclecount/bench_baseline.json at every push). PVSnesLib figures: its 816-tcc + 816-opt on the same C file.

This page has two benchmarks. The first, below, is a static estimate on 34 isolated functions: the cost of the instructions each compiler emits, added up. The second, measured on luna, runs the same C program built by both SDKs and counts the master cycles the machine really spent.

On these 34 functions OpenSNES is about 38 % faster; measured on 23 whole workloads, 62 % (below). What made the difference on code that indexes an array or follows a pointer was not the pointer width: it was the stack frame and stack slots for values PVSnesLib keeps in the direct page, and code the optimiser left dead. Both are gone (see "Reading it" at the end of this page).

OpenSNES's cc65816 compiler (cproc + QBE w65816 backend) wins on arithmetic, comparisons, branches, calls and globals. It loses on code that goes through pointers, where the 4-byte pointer ABI costs more than the optimisations recover. Cycle counts are static estimates, not measurements on hardware.

Methodology

Each function in devtools/cyclecount/bench_functions.c isolates one code generation pattern (arithmetic, shifts, loops, struct access, function calls, etc.). Both compilers process the same source file:

  • PVSnesLib: 816-tcc (C89 compiler) + 816-opt (38 peephole rules)
  • OpenSNES: cc65816 = cproc (C11 frontend) + qbe -t w65816

Cycle counts are estimated by devtools/cyclecount/cyclecount.py, which assigns per-instruction cycle costs based on the 65816 datasheet (assuming 16-bit A/X/Y, no page-crossing penalties).

Analysis

Biggest Wins (>40% improvement)

Function Improvement Why
call_add -90.2% Tail call optimisation — call forwarded directly
compare_and_branch -53.5% Comparison+branch fusion eliminates redundant CMP
global_increment -51.2% .l to .w shortening + inc instruction
clamp -46.8% Comparison chain fusion + dead jump elimination
sub_u16 -44.7% Leaf optimisation + A-register cache

Where PVSnesLib Wins

Function Delta Why
pea_constant_args +12.1% pea.w constant push vs PVSnesLib's direct load
mod_const_10 +3.1% Both use runtime __mod16; slight overhead difference

array_read, array_write and array2d_read are wins (47 cycles against 60, 52 against 65, 86 against 112): a function that calls nothing keeps its temporaries in the direct page, and values stored and reloaded at once, or written and never read, are removed. Every function still starts with a rep #$20 (3 cycles), on purpose: it is what lets assembly call an exported function in either accumulator width.

The pea_constant_args regression is a trade-off: pea.w is smaller in code size (2 bytes vs 3) but costs 1 extra cycle. PVSnesLib's lda #imm; pha is faster but larger. Both approaches are valid.

Inlining. A function marked inline that is short (linear flow, ≤ 8 IR instructions, no nested calls, no allocas) is spliced into its callers, and when every direct call has been spliced its standalone body is not emitted: helper(helper(x)) in call_chain becomes arithmetic. A second inliner takes what that one declines: a static function with exactly one call site in its file, whose address is not used, is inlined with its control flow and not emitted (no keyword needed: the code exists once either way); a static inline function called from several places is copied at each, up to 160 IR instructions (CC_INLINE_MAX_BIG=N). A leaf function, unless it is tiny, stays a function when its caller still calls something else: apart, it keeps the direct-page frame that makes it fast. QBE_NO_AUTO_INLINE=1 turns the second inliner off, to measure.

(†) helper appears as 0 cycles because its standalone is suppressed post-inline. The PVSnesLib values (25 raw, 22 opt) remain the baseline for comparison.

Reproducing

make bench # the 34 functions (cycle counts of the generated code)
make bench-sdk # the 23 workloads on luna, against PVSnesLib's recorded figures
PVSNESLIB_HOME=/path/to/pvsneslib make bench-sdk # the same, PVSnesLib rebuilt from that tree
PVSNESLIB_HOME=/path/to/pvsneslib make bench-twins # whole examples both SDKs have, side by side on luna

Caveats

  • Cycle counts are estimates based on instruction timing tables, not hardware measurements
  • Functions are tested in isolation — real-world code has different calling patterns
  • Loop-heavy functions (loop_sum, byte_store_loop) benefit more from optimisation because the overhead reduction is multiplied by iteration count
  • PVSnesLib's 816-opt is designed for tcc816's output patterns; a different C compiler might benefit differently from its peephole rules

The CI gate

Every push runs make bench and the luna workloads below on the OpenSNES side and fails on a regression: more than 5 % in total, or more than 25 % and 50 cycles on one function (25 % on one workload). The benchmark is narrow — 34 functions and 24 workloads — so it is one check among the others (make tests, the compiler tests).

Measured on luna

Measured with make bench-sdk on luna (the pin in testing/luna.version), PVSnesLib at fa758c9b 2025-12-28, both ROMs LoROM SlowROM. The figures are the two files committed in devtools/sdkbench/; CI re-measures the OpenSNES side at every push.

The same C file, devtools/sdkbench/workloads.c, is built unchanged by both SDKs and run on luna, which is cycle-accurate. It holds 24 small workloads of the kind a game runs every frame (23 that both SDKs build the same way, and one measured for OpenSNES alone). Three things are measured for each: the master cycles it costs (an NTSC frame is 357,368), the bytes of code of its functions, and how deep the stack goes while it runs (bytes below the initial stack pointer).

Of the 23 workloads both SDKs build OpenSNES is faster on 23, no larger on 23, and no deeper in stack on 22. Both ROMs leave the same checksum for each of them, so they computed the same thing.

stepseq is measured for OpenSNES alone and stays out of the totals: built by PVSnesLib's compiler it leaves another checksum than the native build of the same file and than ours, so its time there measures another computation.

How a workload is timed. luna profile credits every master cycle to the symbol being executed. For each SDK the runner builds one ROM per workload and one that runs none, and runs each for the same 900 frames. The two differ only by the workload: its symbols gain cycles, the idle loop loses exactly as many (checked: the two sums are equal), and the NMI handler stays the same. The figure is the sum of the gains — the function, everything it calls, the runtime's multiply and divide — with nothing of either SDK's boot or per-frame handler in it.

Reading it.

  • Every workload is faster, by 32 to 78 %, and none is larger. Divide, modulo and 32-bit arithmetic gain most (decimal −75 %, long −60 %, div32 −59 %), and so do index loops over arrays (physics −78 %, copy −78 %, sieve −73 %). The closest are mul (−32 %), strings (−37 %) and list (−41 %).
  • Why it is faster. The compiler removes values that are computed and never read, branches where a condition is decided instead of storing a 0 or 1 and testing it again, reads arr[i] as lda.l arr,x with the index in X and p->field as lda.l N,x with the pointer in X, and keeps the temporaries of a function in the direct page when no call crosses them.
  • The stack is level or shallower on 22 workloads of 23. grid is the exception (44 bytes against 39): a single large function whose temporaries do not fit the 16 words of the direct-page block.

What is left has named causes — a stack frame in every function that calls another, X reloaded after every instruction that is not an access, a 32-bit read through a pointer still staged in the direct page — and PVSnesLib is itself far from what a person would write (it never uses X or Y as an index: the inner loop of sort is 255 cycles there and 27 by hand).

What this does not measure: the libraries (sprite, background, audio engines) and a whole game.
