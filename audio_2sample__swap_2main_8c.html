Detailed Description

Samples at addresses the game chooses: a resident set and a swap area.

audioLoadSample() puts each sample where the last one ended. A game whose samples do not all fit in the sound CPU's memory keeps some resident and replaces others during play, in places of its own. This ROM does it with audioLoadSampleAt() and audioLoadSampleBeginAt(), and measures what a game needs to know:

  1. Placing: two samples at $2000 and $3000, an ordinary load after them (it goes above), one just below the first (the allocator does not go back), and what audioUnloadSample() gives back.
  2. Refusals: a place below the sample area, at its end, wrapping past $FFFF, on another sample, on the load in steps; a size under 3; the slot being loaded. Each returns its code and changes nothing.
  3. Replacing during play: voice 0 keeps playing the sample at $2000 while the one at $3000 is replaced in steps, then played.
  4. Silence before overwriting: the voice playing the sample to be replaced is left on, stopped just before the first step, or stopped one or two frames before; a luna manifest reads its envelope when the first byte goes, and the ROM times the release itself.
  5. Timing of a note on another voice while a load in steps runs.

Nothing to press: the phases run on their own, the backdrop colour names the phase, and the results are globals the manifests read.

SNES Concepts
  • The sample directory: two 16-bit addresses per sample, any byte
  • A swap area of fixed places in ARAM, filled while voices play
  • Key-off is a release, not a cut: the voice reads its sample until the envelope is down
What to Observe
Backdrop: blue while placing, red for the refusals, green while voice 0 plays over the replacement, yellow for the silence cases, purple for the timing, grey when done.

◆ silence_case()

void silence_case ( u8 c)
static

One silence case: pad plays on the swap voice, then bell replaces it in its place after the action the case names.

pad is first put back where bell will go (a blocking replacement), so each case starts from the same bytes. A control build whose swap_brr holds pad's bytes (data.asm) runs the same code at the same cycles: its sound differs from this one's only where the voice read a byte that changed.
