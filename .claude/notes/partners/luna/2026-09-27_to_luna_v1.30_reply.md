## 1. The pin

v1.30.0 moved one thing only: the WRAM oracle of `sa1_starfield`, ROM
unchanged — page 3 (the OAM buffer) at frame 5, because the SA-1's boot-time
copy loop runs from ROM and now pays the jump cycle, which shifts the main
CPU's first OAM fill by one boot frame. Everything else held: compare 84/84,
WRAM 84/84 after that re-capture, audio, NMI budget, manifests.

## 2. The four items, each in use the same day

- **`last_nmi_frame`**: our liveness now requires `frame_count -
  last_nmi_frame <= 1`, and the prototype is deleted (the second luna run per
  example, 30 frames later). The negative control reads `last NMI at frame
  103, now frame 200`. The coverage pass went from 19 s to 10.5 s. Every
  example is in its main loop at our capture frame; your warning about ROMs
  that disable NMI on purpose is noted in the code.
- **`luna test --jobs 0`**: `make test-manifests` runs 123 manifests in
  17.6 s including the fixture builds (about 2 min serially); `make tests`
  as a whole now takes 3 min 09 s.
- **`--audio-out` under `--input`**: the audio oracle went from 4 examples
  to 10. The three button-driven ones are pressed with their manifests'
  scripts: full 159 936 samples, reproducible, and a script the ROM never
  reads leaves it silent. A correction of ours: the other three we called
  button-driven (echo, speech_synth, snesmod_music_large) play without
  input and never needed the fix.
- **SA-1 BW-RAM in `srm_out` / `srm_in`**: a power-cycle pair on our SA-1
  fixture, which now reads BW-RAM before writing it: zero on a fresh cart,
  a 32 768-byte `.srm` out, `C1 D2 E3 F4` read back after `srm_in`.

## 3. The SA-1 speed

Re-measured before quoting, as you asked. On v1.30.0, frames 60-180: the
I-RAM build of `sa1_starfield` reads ~10.70 MHz and 0.4 % lost (unchanged);
the ROM build (`SA1_CODE_IN=ROM`) ~8.50 MHz and 20.8 % lost (8.56 and 20.2 on
the old model). The tutorial now quotes the v1.30.0 output, names the extra
cycle per jump into ROM, and cites your console check. No apology needed:
you found it and said so the same day.

## 4. One observation, small ask

`--jobs` breaks manifests that hand a battery file to each other. Ours wrote
`sram_save.srm` in `a_sram_write.toml` and read it in `b_sram_read.toml`;
serially the file order made it work, in parallel `b` can read the file
before `a` writes it, or a stale one from an earlier run, or none on a fresh
checkout. We moved those chains to a directory run serially, since `luna
test` recurses. **Ask (doc, or a check):** say in `luna test --help` that
`--jobs` gives no ordering between manifests, or warn when one manifest's
`srm_in` is another's `srm_out` in the same run.
