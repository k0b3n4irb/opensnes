Le zip `linux_arm64` a été retéléchargé et sa somme recalculée : identique.
Les noms d'archives n'ont pas changé.

Ce qu'elle apporte, par ordre d'utilité probable pour vous :

- **`luna state --until-pc SYMBOLE [--hit N]`** : s'arrête juste avant la
  première instruction d'une routine, à son N-ième passage ; la trame et
  la ligne de l'arrêt sont affichées et dans le JSON (`until_pc`). Les
  scripts `--input` restent indexés par trame.
- **`luna state --peek-at SYMBOLE`** : relit tous les `--peek` à chaque
  passage, en un lancement ; `--peek-at-out` écrit un CSV.
- **`[[checkpoint]] at_symbol = "…"`, `hit = N`** dans un manifeste : un
  point de contrôle qui ne bouge pas quand le compilateur accélère le
  code. `--report json` dit où chacun a eu lieu (`symbol_checkpoints`).
- **`luna profile --frames-out / --worst N / --max-frame-mclk /
  --max-lag-frames / --max-lag-run`** : le coût de chaque trame, les
  trames les plus lourdes avec leur table par symbole, et trois seuils.
  Une trame « en retard » est une trame dont la NMI a trouvé le
  processeur en train d'exécuter au lieu d'attendre dans `WAI` : c'est
  la définition que `WaitForVBlank` de votre `crt0` rend exacte.
  `frame_summary.lag_runs` liste les séries de deux trames ou plus.
- **`--peek NOM:0x24` et `NOM:#36`** : un compte qui dit sa base. Un
  compte nu reste en hexadécimal ; s'il se lit aussi en décimal, une note
  le dit sur stderr.

### Ce qui peut bouger chez vous à l'épinglage

- `stats.last_frame` (JSON d'état) partage maintenant à la frontière de
  trame un temps qui la franchit ; avant, une rafale DMA à cheval était
  comptée en entier dans la trame où elle commençait. Son `total` vaut
  exactement la durée de la trame. Les images, le son et les sauvegardes
  d'état ne changent pas.
- La ligne de résumé de `luna profile` gagne des lignes (`frames: …`,
  `lag runs …`). Aucune ne contient `%`, pour qu'un script qui repère les
  lignes de la table par ce caractère ne les prenne pas.
- Un `--peek NOM:36` affiche une note sur stderr. Ce qu'il lit n'a pas
  changé.

## 2. Après la v1.36.0, déjà sur `develop` (`14a6bb8`) : la largeur d'une assertion

Dans `[asserts.values]` et `[checkpoint.values]`, une valeur attendue qui
tient sur un octet ne comparait qu'un octet : `cam_x = 21` passait alors
que la variable valait 277. Quand le `.sym` donne `_sizeof_<nom>` = 2, les
deux octets sont maintenant comparés. `width = 1` garde l'ancien
comportement ; un symbole sans taille connue, un tableau, une adresse et
une clé `symbole+N` aussi.

**Un manifeste qui passait sur le seul octet de poids faible échouera.**
Rejoué sur vos manifestes (`testing/manifests`, ROM de votre arbre de
travail), binaire de la `v1.36.0` puis binaire de `develop` :

```
$ luna test testing/manifests --report json     # v1.36.0   : 133 passés, 0 échec
$ luna test testing/manifests --report json     # 14a6bb8   : 133 passés, 0 échec, mêmes lignes d'échec (aucune)
```

Ce changement n'est dans aucune release. Dites-nous s'il vous gêne avant
qu'il y entre.

## 3. Une question : la `v1.32.0`

Notre règle garde les binaires des cinq versions les plus hautes. Avec la
`v1.36.0`, la `v1.32.0` devrait perdre les siens (le tag reste). Votre
`main` la cite encore (`tools/luna-test/baselines/baselines.json` et
`audio.json` : `"luna_version": "v1.32.0"`). **Nous ne l'avons pas
supprimée.** Dites-nous si votre `main` la télécharge encore ; sinon nous
faisons le ménage.
