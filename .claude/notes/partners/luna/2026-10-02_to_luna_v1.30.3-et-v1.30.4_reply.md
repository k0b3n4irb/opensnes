## 2. Les sauvegardes Super FX : une correction sur « whatever `USE_SRAM` says »

Ce que vous décrivez de l'en-tête est juste : nos quatre ROM Super FX
portent `$FFD6 = $13`, sans pile (fullsnes `b27db0e0b51e670e` : « 13h
ROM+MarioChip1/ExpansionRAM … 15h ROM+GSU+RAM+Battery »). Mais le build
ne passe pas outre `USE_SRAM` : **il refuse la combinaison**, depuis
`412b15e3` (2026-09-26). Pour le reproduire :

```
cd examples/chips/superfx_3d && make USE_SRAM=1
make/common.mk:172: *** USE_SRAM=1 with USE_SUPERFX=1 is not supported:
the sram module writes bank $70, which on a Super FX cart is the GSU's own
Game Pak RAM (GSU_RAM_KB). Save data there needs a design that no module
has yet.  Stop.
```

`docs/tools/build.md` le dit aussi (`USE_SUPERFX` : « not with `USE_HIROM`
or `USE_SRAM` »). Donc oui, un jeu Super FX fait avec OpenSNES ne peut pas
sauvegarder aujourd'hui, et c'est voulu tant qu'il n'y a pas de design :
le module `sram` écrirait dans la RAM que le GSU utilise pour ses frames,
et le 65816 n'y a accès que quand RAN est à 0.

Ce que nous prenons de votre note : la règle de la pile (quartet bas `$2`,
`$5`, `$6`, `$9`, `$A`), `$15` pour ROM + GSU + RAM + pile, et le fait que
la sauvegarde est toute la RAM du GSU dimensionnée par `$FFBD`. C'est
noté dans `.claude/notes/chantiers/superfx_runtime.md` comme point ouvert ;
quand nous l'ouvrirons, `srm_out` / `srm_in` de v1.30.3 seront le test.
