## First, the SNESMOD find

Your §1 finding deserves a line of its own. `ResetSound` clearing KOFF
about 60 SPC cycles after setting it — under the S-DSP's 64-cycle KON/KOFF
poll — is a latent bug in every SNESMOD game built with your SDK and with
PVSnesLib, and the sweep you ran (8 of 161 frames on v1.24.0, 10 on
v1.27.0, 0 on both after one reordered instruction) is exactly how it
should be proven: the interrupt-sampling change only moved *which* frames
were unlucky, and you showed the bug exists independently of it. That the
poll is modelled closely enough to expose it is the best argument we have
had for porting the S-DSP from ares line by line.

Thank you also for measuring our 2026-09-22 predictions and reporting that
they held. The `snesmod_music` realignment — same length, same onset,
best offset 0, energy within 0.02 % — is the right evidence for a
re-baseline.

## 1. `port1` / `port2` in manifests

```toml
port1 = "none"
port2 = "none"
[asserts.values]
pad_connected = 0
```

Same vocabulary as `--port1`: `pad`, `mouse`, `superscope`, `multitap`,
`none`.

**No existing manifest changes meaning.** A port left unset keeps the
inference manifests always had — a `mouse` script puts a mouse in port 1,
a `superscope` script a scope in port 2. A port you set wins.

**A script whose device no port carries is an error (exit 2), not a quiet
pass.** `port1 = "none"` beside a `mouse` script would otherwise feed the
mouse input into nothing and your test would pass — the one outcome a test
must never have. Scripts follow their device wherever it is plugged, as on
the CLI, so `port2 = "mouse"` with a `mouse` script is fine.

Your `padIsConnected()` fixture can move from Python into a manifest.

## 2. `symbol+N` keys

```toml
[asserts.values]
"results+16" = 0xFFFF
```

Accepted wherever a symbol or `BANK:OFFSET` key is — `values`, checkpoint
`values` and `blocks` all resolve through the same function, so one change
covers the three. `symbol-N` and `BANK:OFFSET+N` work too. The key as
written is tried first, so a symbol whose name contains a sign still
resolves as itself; an offset that leaves the 24-bit space is an error, not
a wrap.

**`N` is decimal unless prefixed `0x` or `$`.** This is the one decision
you should check against your own habits. It differs on purpose from
`BANK:OFFSET` and from the `--peek` count, which are hex: an element offset
is arithmetic on an address, and `+16` quietly meaning twenty-two bytes
would be a trap nobody would think to check for. If your tooling generates
these keys, emit `0x` when you mean hex.

Verified against your `superfx_3d.sym`: `oamMemory+16` and `7E:0300+0x10`
read the same word as the raw `$7E:0310`.

## 3. R5 — how fast the SA-1 actually runs

`state.sa1` gains `instructions_executed`. `luna profile` gains an `sa1`
block covering the profiled window:

```
sa1: 4391220 instr, 21441240 clocks (0.0% idle in WAI), 20.2% of busy clocks lost to bus conflicts (rom 4324140, bwram 0, iram 13380) — ~8.57 MHz while running
sa1: accesses 85.9% rom, 14.1% iram, 0.0% bwram, 0.0% other
```

That is **your `sa1_starfield`**, frames 60-180, and it answers the
question you could not: **neither 10.74 MHz nor 5.4 MHz, but about 8.6.**
86 % of its accesses are ROM, so it *is* in the ROM case — but the penalty
only applies while the S-CPU is on ROM at the same moment, and it is not
always there, so a fifth of the clocks are lost rather than half. Your
tutorial's "3x" is right for I-RAM code; for this example the honest
figure is about 2.4x.

For comparison, Super Mario RPG, measured on the released binary over
three 120-frame windows of its no-input intro:

| frames | lost to conflicts | effective |
|---|---|---|
| 60-180 | 0.1 % | ~10.73 MHz |
| 400-520 | 32.4 % | ~7.26 MHz |
| 1000-1120 | 23.9 % | ~8.17 MHz |

The same game swings by a third depending on what the S-CPU is doing at
the time, so an SA-1 speed is a property of a scene, not of a cartridge.
Profile the window your tutorial is about.

**What the numbers are.** luna already modelled what decides the speed —
each SA-1 access pays its region cost plus ares' `conflict()` penalty when
the S-CPU holds the same resource (+1 both in ROM, +2 both in BW-RAM or
I-RAM) — and now keeps the count. Accesses are classified with the same
masks the conflict model uses, so the region split and the per-region
conflict steps cannot disagree. The `--out` JSON has every counter:
per-region accesses and conflict steps, DMA steps, idle steps,
`conflict_share`, `idle_share`, `effective_mhz`.

**Idle time is kept apart, and this matters for your `sa1_hello`.** Our
first version reported it at 21.4 million instructions and 10.74 MHz — with
zero bus accesses. That SA-1 sits in `WAI` for the whole window, and each
parked tick was being counted as an instruction retired. Clocks in `WAI`
are now counted as clocks but not as instructions, and left out of the MHz
figure. `sa1_hello` now reads `0 instr … 100.0% idle in WAI … never ran`,
which is true.

**The window is the profiled one.** The counters are cumulative since
power-on; `profile` reads them at `--from-frame` and at the end, so the
boot does not skew the figure.

The conflict-free, I-RAM-resident case would show `~10.74 MHz` and near
0 % lost — if you want your tutorial to demonstrate both regimes, moving
the starfield's inner loop to I-RAM and profiling the two builds side by
side would make the point with numbers.

## 4. `--superfx-trace-from`

You saw it on `develop`; it is in this tag. One correction to the premise
of your 2026-09-24 note: `--dma-trace-from` takes an **instruction count**,
not a frame — as do `--cpu-trace-from` and `--mem-trace-from` — and
`--superfx-trace-from` follows them, because two sibling flags counting in
different units would be a trap. For frame F, read
`stats.instructions_executed` from `luna state --until-frame F --out -`.

Also worth knowing: the Super FX trace is a ring that keeps the most recent
events once full, so the **end** of the run chooses the window and this
flag trims its head, giving exactly `[from, end]` while that fits under
`--superfx-trace-max`. When `--dma-trace-from` and `--superfx-trace-from`
are both given, luna now bridges to the earlier start first — before, the
later one would have switched the earlier trace on late and dropped its
head.

## 5. One fix you did not ask for

The release PR's fuzzing job found that a forged save-state could kill
the process: a 27-byte blob whose length prefix claims exabytes made the
decoder ask the allocator for them — an abort, not a panic, so nothing
could catch it. Every save-state decode is now capped at 64 MiB (real
states are about 0.5 MB), and a forged length is an ordinary
`load_state` error. If your CI feeds luna `--load-state` files or base64
states over MCP, a corrupted one now fails the call instead of the
runner.
