# 05 — API publique et parcours du développeur de jeu

## Périmètre couvert

- Lu : les 39 en-têtes de `lib/include/snes/` (prototypes extraits, conventions de retour, `extern`, typedefs), `docs/STABILITY.md`, `docs/GETTING_STARTED.md`, `ROADMAP.md` (« The v1.0 gate »), `make/removed_api.txt`, `docs/UPGRADING.md` (survol), `tools/opensnes/src/main.c` (init, find_sdk), `starter/`.
- Exercice réel : `make release RELEASE_DIR=<scratch>` (zip 30,6 Mo, 13 s), extraction dans un dossier neuf, puis **uniquement** GETTING_STARTED chemin A : `doctor`, `init --template game`, `build`, `test`, `run`, `budget`, `upgrade` ; ajout d'un second sprite 16×16 (PNG + `.toml`) ; puis le chemin « Manual setup ». Luna copié depuis le worktree (pas de réseau) au lieu de `scripts/install-luna.sh`.
- Captures luna (`luna state --screenshot`) au repos et pad maintenu (`--input "30:0x900,200:0"`) : le sprite bouge ; second sprite affiché.
- Diagnostics : erreurs volontaires (faute de frappe, module oublié, struct par valeur, variadique, en-têtes standard) avec et sans la passe clang.
- Corpus cartouche : une vérification (taille OBJ / table de caractères 16×16), chunk ids cités en 05-9.

## Points forts

- **Le chemin `init` est le meilleur de sa catégorie.** Chronométré sur le zip publié : extraction 0,94 s, `opensnes doctor` instantané (8 contrôles, dit ce qui manque : « luna — not found — scripts/install-luna.sh fetches it »), `opensnes init my-game --template game` 0,00 s, `opensnes build` 0,32 s, `opensnes test` 0,97 s (« 2 passed, 0 failed »). Un sprite qui bouge au pad, deux tests luna verts, sans rien écrire. Temps humain, lecture comprise : ~4 min. SGDK demande d'installer le SDK (Windows d'abord, Linux par wine ou un portage tiers), de poser `GDK`, de copier un sample et `make -f $GDK/makefile.gen` ; PVSnesLib demande `PVSNESLIB_HOME` (avec ses pièges de chemins sous Windows), de copier un exemple et d'écrire les règles gfx4snes dans le Makefile ; ni l'un ni l'autre n'a de test de projet, de `doctor`, de `budget` ni d'outil de migration.
- **Les actifs sont déclaratifs.** Déposer `res/enemy.png` + 4 lignes de `res/enemy.png.toml` suffit : le build le convertit, génère `res/enemy.inc` (`DECLARE_GFX_ASSET`) et le compte dans « [ASSETS] VRAM 3.0K/64K · CGRAM 32/256 ». C'est l'équivalent du `.res` de SGDK, en mieux outillé (`--json`, `inspect`, `--save`).
- **Les budgets sont visibles à chaque build** : banque $00, bande RAM C, sentinelle data-init, lectures aveugles, port WRAM en NMI ; `opensnes budget` donne ROM banque par banque, RAM, VRAM, CGRAM. Aucun SDK homebrew comparé ne fait cela.
- **La passe clang donne des diagnostics de qualité** : `main.c:69:60: error: call to undeclared function 'padHled' … note: did you mean 'padHeld'?`.
- **La politique de gel existe et est outillée** : `docs/STABILITY.md` (promesse, non-gelé, chemin d'un changement), `make/removed_api.txt` (55 lignes), `changed_api.txt`, `opensnes upgrade` — testé : `./up.c:2: hdmaEnable — changes meaning … 1 << n becomes n` et `BGMODE_MODE1 — removed: use BG_MODE1`, code de sortie 1. Aucun nom `OPENSNES_DEPRECATED` en vigueur (grep vide) : la 1.0 ne traînerait pas de mort-vivant jusqu'à la 2.0.
- **Couverture fonctionnelle d'un vrai jeu** : scènes (`scene.h` push/pop/replace), boucle (`gameloop.h`), animation (`anim.h`), collisions AABB et tuiles (`collision.h`), sauvegarde avec codes d'erreur (`sram.h:118-122`), texte et panneaux (`text.h`, `panel.h`), pads + souris + Super Scope + multitap (`input.h`, `pad_keys[5]`), sprites monde avec caméra et tri (`oamPlaceWorld`), file VRAM avec coût (`vramQueueCost()`, ajoutée sur demande du jeu), deux moteurs audio, RNG, PAL.
- **Prédicats unifiés à 0/1** (`types.h:194-199`, TRUE ramené de 0xFF à 1) : un piège PVSnesLib supprimé.

## Points faibles

**05-1 🟠 — Le chemin « Manual setup » de GETTING_STARTED ne construit pas tel qu'il est écrit (effort S).** Trois défauts mesurés, l'un derrière l'autre :
1. `docs/GETTING_STARTED.md:148` : `OPENSNES := /path/to/opensnes        # where you extracted the SDK`. Dans make, le commentaire en fin de ligne laisse les espaces dans la valeur ; `include $(OPENSNES)/make/common.mk` devient deux mots. Reproduit : `make: *** …/user/opensnes: Is a directory.  Stop.`
2. L'extrait (l.147-152) n'a pas `USE_LIB := 1`, alors que `make/common.mk:110` met `USE_LIB ?= 0`. `LIB_MODULES` est ignoré sans rien dire et le lien échoue : `main.c.o: main.c.wrap.asm:19: FIX_REFERENCES: Reference to an unknown label "textModeInit".`
3. Ajouter ensuite `USE_LIB := 1` **ne répare pas** : `linkfile` (`common.mk:696`) dépend de `.opensnes_config`, dont le texte (`common.mk:620`) ne contient pas `USE_LIB`. Le `linkfile` à 8 lignes reste, et la même erreur revient à chaque `make` jusqu'à `make clean`. Construction périmée silencieuse → expert 03 pour le correctif build.
Conséquence : un débutant qui prend « the long way » se heurte à deux murs cryptiques dans ses cinq premières minutes. Le chemin `init` n'est pas touché.

**05-2 🟠 — Le Makefile généré par `opensnes init` contient le chemin absolu du SDK (effort S).** `tools/opensnes/src/main.c:378` écrit `OPENSNES := <chemin absolu>` (`:=`, l'environnement est ignoré). Reproduit en renommant le dossier du SDK (ce que fait une montée de version vers un autre dossier) : `Makefile:14: …/opensnes/make/common.mk: No such file or directory`. Le Makefile est versionné (il n'est pas dans le `.gitignore` généré), donc un coéquipier qui clone hérite du chemin d'une autre machine. Pourtant le CLI sait déjà trouver le SDK (`OPENSNES_HOME`, puis son propre `bin/`, `main.c:191-199`). SGDK (`GDK`) et PVSnesLib (`PVSNESLIB_HOME`) passent par une variable d'environnement depuis toujours.

**05-3 🟠 — Un module oublié dans `LIB_MODULES` donne une erreur brute de l'éditeur de liens (effort S).** Inclure `<snes/collision.h>` et appeler `collideRect` sans `collision` dans `LIB_MODULES` donne `FIX_REFERENCES: Reference to an unknown label "collideRect".` : ni le module à ajouter, ni la ligne du Makefile. Le build connaît pourtant la correspondance fonction → module (`_DEP_*`, `common.mk:304-313`). Le commentaire de `lib/include/snes.h:130` (« These modules carry real linker / dependency cost when included ») est faux depuis `wlalink -d` : un en-tête ne coûte rien, une section non référencée est jetée. SGDK et PVSnesLib lient une bibliothèque entière, sans cette friction.

**05-4 🟠 — Aucun en-tête standard du C autonome (freestanding) (effort S-M).** Avec `cc65816`, `<stdint.h>`, `<stdbool.h>`, `<stddef.h>`, `<limits.h>` et `<stdarg.h>` donnent tous `fatal error: X.h: No such file or directory` (et `<string.h>` aussi, alors que `snes/string.h` fournit `memcpy`…). C11 §4/6 impose ces en-têtes même à une implémentation autonome. Rien ne le signale dans `KNOWN_LIMITATIONS.md` ni dans `docs/` (grep `stdint|stdbool|freestanding|stddef` vide). Conséquence : le moindre code portable (une bibliothèque de maths, un décodeur, du code venu de GBDK-2020 qui livre ces en-têtes) casse à la première ligne. C'est un ajout, donc compatible avec le gel, mais les largeurs (`int` 16 bits, `long` 32 bits) doivent être choisies avant que les projets ne tapent leurs propres `typedef`.

**05-5 🟠 — `oamInit(size, name_base)` : un numéro de page là où tout le reste du SDK prend une adresse, à corriger avant le gel (effort S).** L'en-tête reconnaît lui-même le piège (`sprite.h:222-237` : « Passing a VRAM address — the natural mistake, since every other VRAM parameter in the SDK takes one — silently yields a wrong base … There is no diagnostic »). Le projet de démarrage passe un `1` littéral (`starter/main.c:45`) et non `OBJ_NAME_BASE(0x2000)`. Corriger après la 1.0 (accepter une adresse quand la valeur dépasse 7) serait un **changement de sens** pour les valeurs aujourd'hui masquées, donc réservé à une version majeure par `STABILITY.md`. C'est le cas d'école du principe « type-safe boundaries » de `PHILOSOPHY.md`, et sa dernière fenêtre est maintenant.

**05-6 🟠 — Le gel figerait des incohérences de nommage, de type et de convention d'erreur (effort M).** Mesuré sur les prototypes publics :
- **Polarité du résultat** : `AUDIO_OK = 0` (`audio.h:149`), `SRAM_OK = 0` (`sram.h:118`), `apuWaitBoot` 0 = succès (`apu.h:43`), mais `scenePush` (`scene.h:202`), `vramQueuePush` (`vramqueue.h:108`) et `gsuPresentInit` (`superfx.h:370`) renvoient 1 = succès. `audioPlaySample`/`Ex` documentent « 0xFF on failure » (`audio.h:380,393`) alors que `audioPlaySampleOn` renvoie `AUDIO_VOICE_NONE` (même valeur, deux vocabulaires).
- **Noms** : `WaitForVBlank` est la seule fonction en PascalCase ; `dmaFillVRAM`/`dmaClearVRAM` contre `dmaCopyVram`/`dmaCopyCGram` ; `objCollidMap`, `objCollidMapWithSlopes`, `objCollidMap1D`, `objCollidObj` (faute héritée de PVSnesLib) ; `consoleMesenBreakpoint` (`debug.h:52`, nommé d'après un outil retiré du projet, et sans rapport avec la console) ; types `t_objs`/`t_sprites`/`t_metasprite` à côté de `Rect`, `Scene`, `GfxAsset`, `OamWorldBatch`.
- **Types** : `oamGetX` renvoie `u16`, `oamGetY` `u8` (`sprite.h:360,372`) ; `bgSetScroll(u8, u16, u16)` mais `mode7SetScroll(s16, s16)`.
Une fois la 1.0 sortie, chaque nom ne peut qu'être doublé d'un alias puis déprécié, et vit jusqu'à la 2.0. Avant la 1.0, `removed_api.txt` et `opensnes upgrade` permettent un renommage net et outillé, comme le lot B l'a fait.

**05-7 🟠 — `STABILITY.md` gèle toutes les variables `extern` des en-têtes, y compris des détails d'implémentation (effort S).** La promesse (« Every documented variable a header declares `extern` keeps its name and type ») couvre `vram_queue_src/bank/addr/size/step[VRAM_QUEUE_MAX]`, `vram_queue_count`, `vram_queue_cost` (`vramqueue.h:56-62`), `objWorkspace` et la disposition de `t_objs` (`object.h:149`), `oambuffer[128]` de type `t_sprites` (`sprite.h:199`), `text_config`, onze variables `gsu_*`/`superfx_status` (`superfx.h:83-143`), `dsp1_o0..3`. Résultat : la structure de la file VRAM, celle du moteur d'objets et l'état interne du Super FX ne pourraient plus bouger avant la 2.0. Il faut séparer la surface voulue (`oamMemory`, `frame_count`, `pad_keys*`) de la plomberie, marquée `@internal` et exclue de la promesse.

**05-8 🟡 — Six fonctions publiques ont plus de cinq arguments, et la décision reste au propriétaire (B PF9) (effort S pour décider).** `bgInitTileSet` (8), `oamSet`, `oamInitGfxSet`, `tileBlitGlyph2bpp` (7), `oamDrawMetasprite`, `oamMetaDrawDyn` (6). Le gel rend la décision définitive : exempter par écrit, ou refondre avant.

**05-9 🟡 — Ajouter un second sprite demande trois savoirs que le projet de démarrage ne donne pas (effort S).** Mesuré : un 16×16 n'est pas affichable sous `OBJ_SIZE8_L32` (OBJSEL n'offre qu'une paire de tailles pour tous les sprites, snesdev-wiki chunk `c2d3d31a61323196` : « two rectangular sizes that sprites can use ») ; le `.pic` d'un 16×16 fait 1024 octets pour 128 octets de dessin, car il est rangé en rangées de 16 tuiles (anomie-regs `e78aec831679a2a4` : « Tile=$ff … made of tiles $ff, $f0, $0f, and $00 ») — le charger à `0x2000` écrase la rangée `0x10` du joueur ; enfin `0x2100`, la tuile `0x0010` et la page `1` sont liés sans que `starter/main.c` le dise. À côté de cela : le commentaire de `starter/res/player.png.toml:2-3` donne des symboles qui n'existent pas (`player_til`, `player_tilend` ; les vrais sont `player_tiles`, `player_tiles_end`), le `.inc` d'un sprite propose `gfxLoad(bg, &player, …)` avec `BG_16COLORS`, et `opensnes-sprite inspect` ignore le `.toml` (« 32 tiles, 1024 bytes » pour un `player.pic` de 2048 octets) → expert 03.

**05-10 🟡 — Un test qui échoue renvoie à une commande que l'utilisateur n'a pas (effort S).** `opensnes test` affiche `fbhash: expected …, got … (run \`luna test --update\` …)` ; luna n'est pas sur le PATH, et la commande du projet est `opensnes test --update` ou `make test-update`. Chaque échec ajoute aussi la ligne `make: *** […common.mk:748: test] Error 1`.

**05-11 🟡 — Deux numéros de version (effort S).** `opensnes --version` → `opensnes 1.0.0`, `opensnes-sprite 1.0.0`, alors que le SDK est en 0.50.0, et `doctor` n'affiche pas la version du SDK. Dans un rapport de bug, « 1.0.0 » trompe.

**05-12 🟡 — Les en-têtes publics racontent l'histoire (effort M).** 136 dates `20YY-MM` dans `snes.h` + `snes/*.h` (superfx.h 11, hdma.h 10, math.h 9…), publiées par Doxygen : la note de `oamSet` parle encore de « the old framesize=158 cliff … RESOLVED », `apu.h:43` de « since 2026-10-03: it waited for ever ». L'ancre 18 du sentinelle ne lit que `docs/` et les exemples. `gameloop.h:15` et `PHILOSOPHY.md:191` citent un module `scene_2d` qui n'existe pas (c'est `scene.h`).

**05-13 🟡 — Coûts annoncés inégaux (effort M).** `docs/PERF.md` et `docs/BENCHMARK.md` mesurent bien les appels courants, mais `map.h`, `object.h`, `collision.h`, `scene.h`, `sram.h` ne contiennent aucun ordre de grandeur (0 occurrence de cycles/scanline/mclk/cost), alors que ce sont les appels qu'un jeu fait par entité et par image (principe 5 de `PHILOSOPHY.md`).

**05-14 🟡 — Ce qui manque à un vrai jeu, sans bloquer le gel puisque c'est additif (effort L).** Moteur de carte : `MAP_MAXMTILES 512` (`lib/source/map.asm:68`), tilemap fixée à $6800 et une seule couche : une grande carte défilant sur deux axes demande d'écrire son propre moteur en anneau. Sauvegarde : somme XOR sur 8 bits (`sram.h:230`), ni version, ni emplacements (reporté à la 1.1 par `ROADMAP.md:64`). Texte : pas d'affichage signé (`textPrintU16` et `textPrintHex` seulement). Pas de caméra générique (zone morte, suivi) hors moteur de carte.

**05-15 🟠 → expert 01 — Deux diagnostics du compilateur trompent l'utilisateur sur l'endroit de l'erreur.** (a) Après un commentaire sur plusieurs lignes suivi d'une ligne à commentaire de fin, les numéros de ligne de cproc sont décalés d'une ligne. Reproduction à 7 lignes : `/* a\n b */\nint x;   /* c */\nint main(void){\n  padHled(0);…` → `d3.c:4:3` au lieu de 5 ; dans le projet de démarrage modifié, `main.c:68:42` au lieu de 69. La passe clang masque le décalage pour ce qu'elle voit, pas pour les erreurs que seul cproc émet. (b) Un struct passé par valeur, que clang accepte, donne `cc65816/qbe: unhandled IR op 109 (parc) … pass a pointer` **sans fichier ni ligne** ; même chose pour un appel variadique (`op 118 (argv)`).

## Risques

- **La 1.0 fige ce que PVSnesLib a laissé** : moteur d'objets (`objCollidMap`, `t_objs`, `objGetPointer` qui renvoie un `u16`) et moteur de carte (constantes `T_FIRES`, `T_PLATE`). Les remplacer après la 1.0 fera vivre deux moteurs jusqu'à la 2.0.
- **La migration d'un projet n'est vérifiée que dans un sens.** `opensnes upgrade` lit `removed_api.txt` (à partir du lot B, 2026-10-05). Les renommages plus anciens (`oamInitEx` fusionné dans `oamInit`, commit `d01b09ef`) n'y sont pas. Peu de projets sont concernés aujourd'hui, mais l'outil se présente comme exhaustif.
- **`docs/STABILITY.md` couvre « the asset formats the tools produce »**, mais pas les fichiers `.toml` de réglages ni les noms de symboles générés (`<stem>_tiles`, `<stem>_pal`…) que tout `main.c` tape. Un renommage dans `opensnes-sprite` casserait chaque projet sans violer la lettre de la promesse.
- **Windows n'a pas été rejoué** (MSYS2) : le chemin absolu de 05-2 et les espaces de 05-1 y sont plus fréquents (`C:\Users\Prénom Nom\…`).
- Le jeu se construit sur `develop` : les correctifs de 05-5 et 05-6 touchent des en-têtes publics, donc ils vont dans un worktree séparé (`exchanges.md`).

## Verdict

Le parcours `opensnes init → build → test` est le plus abouti que j'aie vu sur une console rétro : un projet jouable et testé en moins de cinq minutes, des budgets visibles et un outil de migration qui fonctionne, là où SGDK et PVSnesLib laissent tout cela à l'utilisateur. Sous la surface, l'API publique n'est pas encore prête à être figée : un piège reconnu (`oamInit`), des conventions d'erreur et de nommage contradictoires, et une promesse qui gèle la plomberie interne. Une fois la 1.0 publiée, ces défauts ne pourront plus être corrigés qu'à la 2.0. Le chemin manuel du guide, le Makefile non portable, l'erreur de lien muette et l'absence de `stdint.h` sont des frictions peu coûteuses à corriger, qui doivent l'être avant que la 1.0 n'attire ses premiers utilisateurs.
